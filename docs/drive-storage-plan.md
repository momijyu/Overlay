# Drive保存と端末内データの方針

2026年11月4日のユーザー確認を反映する。以下は最終的な保存方針であり、通常保存のDrive切り替え・キャッシュの自動削除はまだ利用できない。段階的な実装として、ノート1件の手動保存・確認付き同名上書き・コピー読み込みを追加した。

## 最新の実装状況

続く指定で、選択したノート1〜200件の一括手動保存を追加した。新規／上書きを一覧で確認し、本文は1件ずつ取得・送信する。失敗したら後続を止め、成功分を除いて再確認できる。フォルダのチェック済み子ノートも対象だが、階層・空フォルダ自体のDrive複製は含まない。自動保存先やキャッシュ整理の実装状況は変えない。操作手順と部分成功・中断の制約は[Driveのノート](./google-drive-notes.md)を参照。

Chrome・localhost:3000でのGoogle認可・本人アカウント・Overlay専用フォルダに加え、新規保存と一覧表示もユーザー画像で確認済み。コピーもできていそうとの利用者報告を受け、同じPDF本体・書き込みの復元は追加しないよう変更した。異なる内容は確認後に別ノートとして追加する。今回の重複防止は実機未確認。手順と形式は[Driveのノート](./google-drive-notes.md)を参照する。

現在のコピーは再取得可能なキャッシュとして管理しておらず、IndexedDBの通常ノートとして保持する。比較用キャッシュやDBストアは追加しない。同一内容の再復元は増えなくなるが、異なる内容の復元で使用量が増えることは防がない。通常保存とキャッシュを区別してから下記の500MB整理を実装する。

自動保存は引き続きIndexedDBへ行い、既存の全ノートを自動送信しない。最新指示で、一覧のノート1件からの保存と、同名が1件なら注意付き上書きを追加した。同じPDFはDriveのSHA-256・サイズと照合して再送せず編集JSONのみ更新する。PDFが異なる・照合不可なら新しいPDFを送り、旧PDFは削除しない。手動上書きは事前の版比較を行うが原子的な競合防止ではなく、他端末と同時保存しないことを案内する。自動同期へ流用しない。送信待ちの永続化とキャッシュ整理、正式保存時の競合保護は後続。

## 先行した接続準備

ノート一覧の「Google Driveの接続確認」でメールアドレスとアプリ専用フォルダを確認できる。氏名は表示しない。一般の同名フォルダは使わない。閉じると通信を中断し、認可は同じページのメモリ内で有効期限まで再利用する。再読み込み・失効後は再接続する。通常の自動保存はまだIndexedDBのままで、対象確認後にだけDriveへ送信する。手順は[Google側の設定](./google-drive-setup.md)と[保存操作](./google-drive-notes.md)を参照。

正式な自動保存の競合制御は未実装。事前にDriveの版を取得しても、その後の更新直前に他端末が書き換える可能性がある。条件付き更新の契約・実API動作を検証してから正式保存へ接続する。現在の手動上書きはこの保証を満たすものとは扱わない。

## 保存先

- Drive連携中は、利用者本人のDriveを正式な保存先とする。運営者の個人Driveを全利用者で共有しない。
- IndexedDBは、必要なファイルのキャッシュと未送信の編集内容を保持する。全ノートのPDF・編集本文を端末へ複製し続けない。
- Drive未連携時はIndexedDBが保存本体。接続しただけで既存のローカルノートを送信せず、対象を確認する。
- 接続切れ・権限失効で、Driveノートを勝手にローカル専用ノートへ切り替えない。未送信として保持し、再接続・再試行を案内する。
- SQLiteへの置換と、OS上のPDFのパスだけを保存する方式は採用しない。PC・iPadで利用できることを優先する。iPadの実機確認は必要であり、現時点の対応完了を意味しない。

## キャッシュの上限

利用者は初期上限として500MBを選択した。実装上は500,000,000バイトとし、Driveから再取得できる元PDFと編集本文の合計を対象にする。通常保存全体・ブラウザの保存可能容量・メモリ使用量・バックアップファイルの安全上限とは別の値である。

- 容量と最終利用時刻を管理し、必要になったノートだけ取得する。上限に達する前に、再取得できる古いキャッシュから整理する。
- 元PDFと対象の編集版がDriveへ保存済みで、未送信の変更や競合がなく、編集中でないことを削除条件にする。一覧情報は残し、キャッシュを消してもDrive上のノートを削除しない。
- 未送信・保存失敗・競合中・ローカル専用のデータはキャッシュ整理で削除しない。送信中に新しい編集があれば、古い版の送信成功だけで新しい版まで保存済みにしない。
- 編集中のデータは保護する。単体でキャッシュ上限を超えるPDFの扱いとメモリ上限は別に検証し、黙って上限を拡大したり元データを削除したりしない。
- 保護対象が増えればIndexedDB全体は500MBを超え得る。使用量とブラウザの容量推定を確認し、容量不足時は保存失敗を知らせ、同期・書き出し・不要ノートの整理を案内する。未送信データを消して空けない。
- キャッシュを整理したノートは再度の通信が必要。全ノートのオフライン利用や、アプリ終了後の常時同期は保証しない。

初期段階では、オフライン利用の固定指定・キャッシュ設定画面・自動的な上限拡大は追加しない。必要なら別途利用者と確認する。

## 編集と送信

確定した編集をまずIndexedDBへ保存し、Driveへ順に送る。送信待ちは最新の確定内容へまとめ、操作ごとのPDF複製や無制限の送信履歴を作らない。端末保存とDrive保存の完了を区別し、失敗時は内容を維持する。アカウントごとに参照先・キャッシュ・送信待ちを分離し、別アカウントへ送らない。他端末の変更は黙って上書きせず、両方の内容を保護して解決する。

Driveの元PDF・編集情報は分ける。編集ごとにSQLite全体・全ライブラリZIP・書き込みを焼き込んだPDFをアップロードする方式にはしない。OAuthは11月4日の追加回答でGIS token modelに決定した。認証情報はメモリだけに保持し、期限切れ時は操作によって再接続する。安全な競合検出・保存手順は引き続き公式資料と実機検証で確定する。

## 先行実装：一覧の軽量化

`localDatabase.ts`のDB版を1から2へ更新し、`noteSummaries`を追加した。ID・ノート名・元ファイル名・所属フォルダ・更新日時だけを保存する。既存の`notes`・`pdfs`・`folders`は残し、PDFや線・文章を移動・削除しない。初回更新では旧ノートをカーソルで1件ずつ読み、一覧情報だけを追加する。移行失敗時は版更新ごと取り消す。初回移行は全ノートを一度走査するが、全編集本文の`getAll()`は使用しない。

`localNotes.ts`の一覧取得・階層検証は`noteSummaries`と`folders`だけを読む。編集時に対象の本文・PDF、バックアップ時に対象ノートの本文・PDFを読む。保存・整理・削除・復元は一覧情報も同じトランザクションで更新し、途中失敗ならまとめて取り消す。`localNoteSummary.ts`が一覧に含める5項目を共通化する。

これは一覧を開くときの読み取り負荷を減らすものであり、保存済みPDFの容量を減らす処理ではない。一覧用の小さな情報分だけ保存量は増える。現時点では全一覧情報を取得しており、大量件数へのページ分割や仮想化、キャッシュ上限・自動削除・Driveへのノート保存は未実装。バックアップの版1・2と編集データの形式は変更しない。

DB版2へ更新後は、版1だけを開く古いアプリでは操作できない。他の古いOverlayタブを閉じて更新版を読み込む。サイトデータの削除やDBの手動初期化は不要。今回のテストは隔離したメモリ内DBのみで、実ブラウザの利用者データを操作していない。
