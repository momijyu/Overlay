# Supabase保存機能の設定

## 現在の保存先について（2026年10月15日）

現在の通常画面はブラウザ内のIndexedDBへ保存し、このページのSQL・環境変数・匿名認証を必要としません。以下は旧Supabase版の記録です。既存のクラウドデータ・設定・セッションは削除していません。移行は未対応であり、ローカル一覧が空でもSupabaseデータが削除されたことを意味しません。確認のためにテーブルやサイトデータを削除しないでください。

第2回では、元PDFとペンの書き込み情報を分けて保存する。第3回では、階層型のサイドメニューから保存済みノートを開き、書き込みを再開する。第3回で追加したフォルダ機能には、新しいSQLを1回実行する。第2回のSQLは再実行しない。

第2回で使う認証は、ユーザー確認済みの匿名認証だけとする。サインイン画面と個人アカウント管理は第6回の対象であり、今回は追加しない。

## 1. 匿名サインインを有効にする

Supabaseのプロジェクト画面で、Authenticationの「Sign In / Providers」を開き、「Allow anonymous sign-ins」を有効にして保存する。設定の説明は[公式のGeneral configuration](https://supabase.com/docs/guides/auth/general-configuration)を参照する。

これはメールアドレスやパスワードを入力する画面を追加せず、保存したブラウザを識別するための設定。同じブラウザ・同じサイトで識別情報が保持される。ブラウザのサイトデータを削除した場合、プライベートブラウズを終了した場合、別のブラウザ・端末・サイトURLを使った場合は、同じ識別情報を利用できない。

詳細は[Supabaseの匿名サインイン](https://supabase.com/docs/guides/auth/auth-anonymous)を参照する。

## 2. 保存先とアクセス制限を作成する

SupabaseのSQL Editorで新規クエリを開き、[202610050001_notes.sql](../supabase/migrations/202610050001_notes.sql)の内容を貼り付けて、1回だけ実行する。

このSQLは次のものを作成する。

- `notes`テーブル: ファイル名、元PDFの保存場所、ページごとの線データ、保存日時を記録する。
- `overlay-pdfs`バケット: 元PDFを非公開で保存する。
- RLS: ノートとPDFへのアクセスを、保存した識別情報の所有者だけに制限する。

SQL全体をトランザクションで実行するため、途中でエラーになった場合は作成途中の変更が残らない。成功後に同じSQLを再実行すると、作成済みのテーブルなどと重複してエラーになる。

### 第3回のフォルダ用SQL

第2回の保存設定が済んでいるプロジェクトで、SQL Editorの新規クエリに[202610120001_note_folders.sql](../supabase/migrations/202610120001_note_folders.sql)の内容を貼り付け、1回だけ実行する。ローカルのファイルを変更しただけでは、このSQLはSupabaseへ自動適用されない。

- `note_folders`: フォルダ名、親フォルダのID、所有者のIDを保存する。
- `notes.title`と`notes.folder_id`: ノート名と所属先を追加する。既存ノートは未分類のまま最上位へ表示する。
- フォルダのRLSと所有者を含む外部キー: 他の所有者のフォルダを参照・作成先に指定できないようにする。

元PDF、線データ、既存のノートIDは変更しない。SQLの設定前は、従来のノートを最上位に表示し、フォルダ作成と名前・保存先の変更だけを無効にする。設定後はメニューの「更新」を押す。

第3回のフォルダ操作は作成、開閉、移動に加え、最新のユーザー指示で名前変更と空フォルダ削除を補完する。名前変更・削除には以下の管理用SQLも必要になる。子要素のあるフォルダの削除は含めない。

### 第3回のフォルダ移動用SQL

フォルダ作成用SQLの実行後、新規クエリに[202610120002_folder_moves.sql](../supabase/migrations/202610120002_folder_moves.sql)を貼り付けて実行する。この移動用SQLは`create or replace function`に修正済みで、同じ関数がある環境でも再実行できる。「function already exists」となった環境では修正後のファイルを使う。テーブル作成用の第2回・フォルダ作成用SQLは再実行しない。このSQLの適用だけでは既存データを移動・削除しない。

`move_note_folder`は認証情報から所有者を確認し、同じ所有者のフォルダへの移動だけを許可する。子孫・自分自身への移動は拒否し、同名フォルダとの衝突は既存の制約で防ぐ。テーブルの直接UPDATE権限は増やさない。アプリはSupabaseの`rpc()`でこの関数を呼ぶ。

このSQLが未設定でも、ノートの移動と従来の保存・読み込みは利用できる。フォルダの移動時には設定を案内するエラーが表示される。

### 第3回のフォルダ管理用SQL

フォルダ作成用SQLの実行後、新規クエリに[202610120003_folder_management.sql](../supabase/migrations/202610120003_folder_management.sql)を貼り付けて実行する。名前変更と空フォルダ削除の関数を追加する。同じ定義で再実行でき、SQLを適用するだけでは既存のフォルダ・ノート・PDFを変更しない。

テーブルの直接UPDATE・DELETE権限は増やさない。関数内で認証された所有者を確認し、空でないフォルダは拒否する。子フォルダやノートへの削除連鎖はない。管理用SQLが未設定でも従来機能は使え、名前変更・削除時にはSQLの設定案内を表示する。

## 3. ローカルの接続先を設定する

プロジェクト直下の`.env.local`に次の環境変数を設定する。値はSupabaseのConnect画面で取得する。今回のローカル環境には設定済み。

```dotenv
NEXT_PUBLIC_SUPABASE_URL=プロジェクトURL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=公開用キー
```

公開用キーはブラウザからSupabaseのAPIへ接続するために使う。データの保護は、キーを隠すことではなくRLSのアクセス制限で行う。`secret`や`service_role`のキーはここに設定しない。

`.env.local`は`.gitignore`で除外されている。環境変数を追加・変更したら、開発サーバーを再起動する。

## 4. 保存を確認する

1. `npm run dev`で起動し、PDFを読み込んで線を描く。
2. 「ノートを保存」を押し、「保存済み」が表示されることを確認する。
3. SupabaseのTable Editorで`notes`に1件のデータがあり、`file_name`、`pdf_path`、`strokes_by_page`が入っていることを確認する。
4. Storageの`overlay-pdfs`に、ユーザーIDのフォルダと元PDFがあることを確認する。保存されたPDFに線が焼き込まれていないことも確認する。
5. 画面を開いたまま線を追加し、「未保存の変更があります」の表示後に再度保存する。
6. `notes`の同じ行で`strokes_by_page`と`updated_at`が更新され、PDFが重複して増えていないことを確認する。

保存中に線を追加した場合、その線は次の保存の対象になる。最初の保存処理が完了しても「未保存の変更があります」と表示する。

第3回では、次の手順でアプリからの再読み込みも確認する。

1. 保存したノートが左の「ノート」メニューに表示されることを確認する。
2. ブラウザを再読み込みし、ノート名を押す。元PDFと、各ページに描いた線が元の位置・太さで表示されることを確認する。
3. 線を追加して保存し、再読み込み後に開き直す。追加した線が残り、`notes`の行数とStorageのPDF数が増えていないことを確認する。
4. 別のPDFも保存して一覧から切り替え、それぞれのPDFと線が混ざらないことを確認する。
5. 未保存の線を描いて別のノートを開こうとする。「キャンセル」では元の内容が残り、切り替えを承認した場合だけ別のノートが開くことを確認する。

フォルダ用SQLの実行後は、次の操作も確認する。

1. 「最上位」を選び、「フォルダ作成」でフォルダ名を`2026`、作成先を「最上位」にして作成する。
2. `2026`を選んで「フォルダ作成」を押す。作成先が`2026`になっていることを確認し、名前を`情報`にして作成する。
3. PDFを読み込み、線を描いて「ノートを保存」を押す。新しいノートは最上位へ保存される。
4. 保存したノート名を選び、「操作 → 名前・保存先」を押す。ノート名を`ノート1`、移動先を`2026 / 情報`にして「変更」を押す。`2026 → 情報 → ノート1`の順に表示されることを確認する。
5. フォルダ名を押すと子を開閉できること、上の「ノート」ボタンでメニュー全体を隠して戻せることを確認する。メニューを隠しても編集中のPDFと線は残る。
6. 再読み込み後も階層と名前が残り、フォルダを展開してノート名を押すと元PDFと線が復元されることを確認する。
7. 線を追加して再保存する。ノート名・所属先が変わらず、元PDFとノートの件数が増えないことを確認する。
8. ノートを選んで「操作 → 名前・保存先」で「最上位」に戻せること、同じ親の下に同名フォルダを作ろうとするとエラーになることを確認する。
9. 作成・変更画面をキャンセル・Esc・背景クリックで閉じて、一覧の操作とドラッグを再開できることを確認する。保存中は閉じられず、失敗時は入力とエラーが残ることも確認する。

フォルダの開閉とメニュー全体の表示状態は画面内の状態であり、再読み込み後には初期状態へ戻る。フォルダ構造とノート名・所属先はSupabaseへ保存する。

ドラッグ移動は、移動用SQLの実行後に次の手順で確認する。

1. 最上位に`2027`も作成する。保存済みノートをフォルダ名の上へドラッグし、移動先が強調されること、落とすとその中へ移動することを確認する。
2. `情報`フォルダを`2027`の名前の上へ落とす。`情報`の中のノートや子フォルダもそのまま残ることを確認する。
3. ノートやフォルダをメニュー上部の「最上位」へ落とし、外へ戻せることを確認する。
4. フォルダを自分自身や子孫へ落とそうとしても移動しないこと、移動先に同名のフォルダがある場合はドラッグ時点で無効になり元の階層が残ることを確認する。大文字・小文字だけが違う名前も衝突とする。別タブでの変更などで一覧が古い場合もDBが衝突を拒否する。
5. 移動後に再読み込みし、階層が残ること、元PDFと線が復元されることを確認する。編集中の未保存の線も、移動だけでは消えないことを確認する。
6. フォルダを選んで「操作 → 移動」からも移動できることを確認する。「（現在）」の場所では移動せず、理由を表示する。ドラッグしにくい環境では、ノートは「操作 → 名前・保存先」を使う。
7. 移動中は別の移動・PDF切り替えができず、一覧の取得中は移動ができないこと、ドラッグを中断した場合は保存先を変更しないことを確認する。
8. 閉じたフォルダ名にドラッグしたまま約600ms待つと開き、その中の子フォルダへ移動できることを確認する。現在の親でも開けるが、現在の親への移動自体は行わない。途中で離れたり中断したりすると展開しない。
9. 移動先フォルダの直下のノート名や、子一覧の余白に落としてもそのフォルダへ入ることを確認する。子フォルダ名やその内部に落とす場合は、その子フォルダを優先し、親と子へ二重に保存しない。最上位のノート上なら最上位へ戻る。強調されたフォルダが実際の移動先と一致することも確認する。

ドラッグは同じ画面内のノート・フォルダの移動に限る。OSのPDFファイルを落としてアップロードする操作、別のタブからの移動、表示順の手動並び替えは対象にしない。

管理用SQLの適用後は、次の操作も確認する。

1. ノートを含むフォルダを選び、「操作 → 名前変更」で名前を変える。階層と保存先表示が更新され、子のノート・PDF・線が変わらず、再読み込み後も新しい名前が残ることを確認する。
2. 同じ親の下の同名フォルダ名を入力すると、エラーと無効な「変更」ボタンになることを確認する。現在の名前のまま・空白だけでも送信できないことを確認する。
3. 空のテスト用フォルダを作成し、「操作 → 空フォルダ削除」で名前と確認文が出ることを確認する。まずキャンセルし、残っていることを確かめる。削除は元に戻せないため、必要なフォルダでは試さない。
4. 同じ空フォルダを確認後に削除し、一覧とSupabaseから消えること、親や他のノート・PDFに変化がないことを確認する。
5. 子フォルダ・ノートのあるフォルダでは削除が無効になることを確認する。確認画面を開いた後、別タブで子が追加された場合もDBが削除を拒否する。
6. 名前変更・削除中は二重送信やPDF切り替えを止め、失敗時は確認画面とエラーが残り、キャンセルではデータが変わらないことを確認する。

確認は、保存時と同じブラウザ・同じサイトURLで行う。別の識別情報では一覧は空になる。

表示倍率は50～200%で切り替えられる。100%は画面に収まる初期表示の大きさを基準にする。線を描いてから倍率を変え、PDFと線の位置が重なること、拡大時に横スクロールできること、別のページへ移動して戻っても線が残ることを確認する。倍率を変えるだけでは保存データは変わらない。

## 5. Vercelの接続先を設定する

VercelのOverlayプロジェクトのEnvironment Variablesに、`.env.local`と同じ2つの環境変数を設定する。Productionで保存する場合はProductionを対象にする。

`NEXT_PUBLIC_`の値はビルド時にブラウザ用コードへ組み込まれるため、設定したあとに新しいデプロイを行う必要がある。commit・pushはユーザーが行う。

ローカルと公開環境はサイトURLが異なるため、匿名の識別情報も別になる。公開環境では`https://overlay-virid.vercel.app/`を継続して使う。
