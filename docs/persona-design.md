# Overlay ペルソナ設計シート

更新日：2026年10月19日

## この資料の位置づけ

企画者本人のアイデア・課題意識を起点に、AIによる文章化支援と、その後の議論をまとめた検討用の資料。企画の原案をAIが考えたものとして扱わない。

### 作成・検討の分担

- 企画・原案・方針の決定：ユーザー本人（Overlayの企画者）。自身の利用経験や考えをもとに、対象利用者と解決したい課題を提示する。
- プロンプト・設計案の文章化支援：Antigravity。企画者の考えをもとに文章や項目を整理する。
- 検討・整理・Markdown化：Codex（OpenAI）。設計案への意見出し、現行仕様との整合確認、仮説と確認済み事項の区別、この資料の編集を支援する。

AIからの追加提案は検討材料であり、採用・優先順位・実装範囲の最終判断は企画者本人が行う。

利用者像・場面・課題は、現時点では実際の利用で確かめるための仮説として扱う。「大学生全体がこの使い方をする」「他製品に同様の機能がない」とは断定しない。機能候補の記載は実装開始や第4回の範囲変更を意味しない。

正式な仕様と開発範囲は[PROJECT.md](../PROJECT.md)と[制作計画書](../software_creation_plan.txt)を参照する。採用する内容はユーザーと確認してから反映する。2026年10月19日の指示で「ページ見出し機能」は第5回の計画に採用したが、実装はまだ開始していない。その他の候補や利用者像の仮説とは区別する。

## 1. ターゲットペルソナ像

| 項目 | 内容 |
|---|---|
| 属性 | 大学の配布PDFを講義・自習で使う学部生・大学院生。まずは自分自身の使い方を起点にする |
| 使用デバイス | ノートPC（Mac / Windows）またはタブレット（iPad等）。両方を併用する場合の端末間連携は別途検討する |
| ノート作成スタイル | 白紙から長いノートを作るより、配布PDFの該当箇所へ短い補足・疑問・注意点を書き足す |
| ツール利用傾向 | 予定はカレンダー、長文やまとめはNotion等の別ツールで管理し、PDFツールにはメモの手軽さを求める、という想定 |
| 残したいもの | 教員の口頭説明、重要箇所、分からなかった理由、訳語、引用候補、修正指摘 |
| 見返すときの目的 | 資料全体を読み直す前に、自分が書き込んだ場所へすぐ戻りたい |

「白紙ノートをほぼ作らない」は今回の対象者の仮定であり、大学生全体の傾向として扱わない。

### 現在の保存方式との区別

現在の通常保存先は、同じ端末・ブラウザ・サイトのIndexedDB。PCとiPadで同じ編集内容を自動共有する機能はない。

「どちらかの端末で完結して使う」と「授業ではiPad、自宅ではPCで続きを編集する」は異なる利用条件。後者を必須にする場合は、同期または編集可能なデータの受け渡しについて別途設計が必要になる。既存のPDF出力では元の編集状態・階層を完全復元できない。

## 2. 主な利用シーン

以下のページ数や記入量は説明用の例であり、利用調査で確認した数値ではない。

### ① 大量スライド講義でのピンポイントメモ

- 状況：50〜100ページ程度の配布スライドを見ながら受講する。
- 行動：全ページを写さず、教員の「重要」「試験範囲」という説明や短い補足だけを書き込む。
- 見返す場面：試験前に、その数ページだけを探したい。
- 想定する不便：80ページ中3〜4ページにしかメモがなく、全ページを順に確認しないと見つからない。

中心候補は、この「講義中に短く記録し、試験前に該当箇所へ戻る」という一連の使い方。

### ② 過去問・演習プリントの解き直し

- 状況：過去問や演習問題のPDFへ計算・解答を書き込む。
- 行動：解けなかった理由や「後で友人に聞く」「要見直し」を残す。
- 見返す場面：間違えた問題や理解が曖昧な問題だけを解き直す。
- 想定する不便：解答を書いたページと、重点的に復習したいページを区別できない。

### ③ 論文・参考文献の精読

- 状況：ゼミやレポートのため、論文や長文のPDF資料を読む。
- 行動：専門用語の訳や「レポート第2章の根拠として使う」といった注記を該当段落の横に残す。
- 見返す場面：レポートを書くとき、メモした文章と元の文脈を確認する。
- 想定する不便：別のメモ帳へ書くと、元資料のどの図・文章に対応するか分からなくなる。

### ④ 提出前レポートのセルフ添削

- 状況：自分のレポートをPDFにして、提出前に見直す。
- 行動：誤字や説明不足、構成の違和感にペンや短文で指摘を残す。
- 見返す場面：元の文書編集ツールに戻り、指摘した箇所を修正する。
- 想定する不便：修正すべき場所や未対応の指摘を探し直す必要がある。

PDF上の赤入れは原稿本文の自動修正とは別。元のWord等へ変更を反映する連携は現在の機能ではない。

## 3. 解決したい課題

### 第一候補：どこにメモしたか分からない

書き込む量が少なくても、後で見つけるために資料全体を探す手間がかかる。メモを書く操作だけでなく、書いた場所へ戻る操作を短くする。

### 第二候補：資料とメモが分断される

別のメモ帳に記録すると、どのページ・図・段落について書いたかが曖昧になる。元の資料と対応する位置にメモを置く。

### 検証したい課題：既存ツールの操作負担

対象者が必要としているのは短い追記なのに、取り込み・整理・多数の機能の選択を負担に感じている可能性がある。具体的にどの操作で困るのかは、利用者の実体験で確認する。

既存アプリ全般について「高額」「重い」「画像化が必要」と一括して断定しない。GoodnotesはPDFの直接読み込みに対応しているため、画像化が必須という比較は使わない。参考：[Goodnotes公式の読み込み手順](https://support.goodnotes.com/hc/en-us/articles/7353717816463-Import-files-into-Goodnotes)。

## 4. 提供したい中核価値

1. 配布PDFの該当箇所へ、短いテキストや手書きを直接置ける。
2. 自分の書き込みがある場所を一覧で把握し、元のページへすぐ戻れる。
   試験対策では、ページに「何があるか」を自分の言葉で見出しとして残し、自分用の目次から探せるようにする。
3. インストールせずブラウザから利用でき、必要なノートは個別PDFとして取り出せる。

「ブラウザ完結」は現在の構成に合うが、「軽快さ」は検証する品質目標。大量ページやiPadでも快適かは、実際のPDF・端末で確認する必要がある。

## 5. 採用したタスクと追加候補

ページ見出し機能はユーザー指示により計画へ採用済み。それ以外は検討案であり、いずれも追加実装はしていない。他製品にない独自機能であることも、まだ検証していない。

### 第5回の採用タスク：ページ見出し機能

授業中に短いメモや見出しを残し、試験前には「何についてのページか」で探す使い方を想定する。メモしたページ数の表示やページ番号だけの一覧ではなく、利用者自身が思い出せる呼び名を付ける。

見出しの例：

- 8ページ：「この公式を使える条件」
- 15ページ：「試験に出ると言われた計算問題」
- 22ページ：「前回間違えた符号の考え方」

計画に含める内容：

- 必要なページだけに見出しを追加・変更・削除でき、入力を必須にしない。
- 書き込みがなくても見出しだけを付けられる。
- ノートごとのページ番号・見出し一覧から該当ページへ移動できる。
- 見出しを元PDFとは別に保存し、開き直しても復元できる。見出しのない既存ノートはそのまま扱う。

ページ内の補足を書くテキストボックス、疑問などを残す付箋、後から探す入口となる見出しは役割を分ける。「重要」「要復習」などの目印は別の任意機能候補とし、このタスクには自動追加しない。

入力方法・一覧の配置・PDF出力への反映は実装前の確認事項。第4回のv1.0.0必須範囲には加えず、第5回の開始指示後に実装する。

### 優先候補：書き込みを再発見する

1. ペン・テキストの書き込みがあるページだけを一覧表示する。
2. 一覧から該当ページへ直接移動する。
3. 前・次の書き込みページへ移動する。

付箋を手動で貼ったページだけに限定しない。目印を付け忘れても、ペンやテキストを書いた事実からページを見つけられるようにする案。書き込みがあるページの判定と、手書き内容を文字として検索するOCRは別の機能として扱う。

### 次の候補：残した理由を区別する

- 「重要」「要見直し」「質問」などの目印。
- メモの種類による絞り込み。
- 疑問・修正指摘の確認済み／未確認の区別。
- PDFをまたいだ未解決メモの一覧。

まず「書いた場所を探せない」という課題を中心に検証する。「何が分からなかったか忘れる」という課題への支援は、関連するが別の追加候補として考える。

### 現時点で中心にしないもの

- 一般的な予定管理やカレンダー。
- 日時を指定した通知・リマインド。
- 白紙ノートの作成や長文の整理。
- AIによる自動要約や問題生成。

予定・リマインドを検討する場合も、一般的な予定帳ではなく「この課題PDFの未確認箇所へ戻る」という資料との関係から必要性を確かめる。

## 6. 第4回との関係

既存計画の第4回は、テキスト追加・編集・削除、ペンの色変更・線の削除、Undo / Redo、それらの保存・再編集・PDF出力と検証によるv1.0.0の完成。

付箋・目標はこれまでの合意では原型完成後の追加要素。今回提案した書き込みページ一覧・絞り込み・未解決管理も、第4回の確定範囲として自動追加しない。第4回へ含めるか、完成後の追加機能にするかは、ユーザーと優先順位・作業量を確認してから決める。

2026年10月19日の最新指示により、ページ見出し機能だけは第5回のタスクとしてPROJECT.md・制作計画書へ反映した。第4回の範囲は変更せず、付箋・絞り込み・未解決管理などを一緒に採用したことにはしない。今回の計画更新ではアプリの実装は行わない。

## 7. 利用者に確認したいこと

- 直近の講義資料は何ページあり、そのうち何ページへメモしたか。
- 後でメモを探した場面はあるか。どう探し、何が面倒だったか。
- 困るのは「書いた場所が分からない」ことか、「何を見直すべきか忘れる」ことか。
- 現在のツールで便利な点と、乗り換えてまで改善したい点は何か。
- 主に使う端末は何か。同じノートをPCとiPadで引き継ぐ必要があるか。
- まず書き込みページ一覧だけで役立つか、メモの内容・種類まで確認できる必要があるか。

検証には、自分の実際の資料で「メモした箇所を探す」操作を行い、候補の仕組みで手間が減るか確認する。現時点で効果測定の結果や利用者の反応を作らない。
