# Drive速度改善の調査（2026年11月10日）

コード・既存の計測記録・公式資料を照合した調査。今回、アプリケーションコードや保存形式は変更していない。実Google Driveでの新しい速度計測も行っていない。

## 現時点の根拠

既存結果の詳細は[速度計測の記録](drive-performance.md)を参照する。

- 11月8日の記録では、キャッシュ済み資料の表示は約0.13〜0.14秒、別の未取得資料は約3.79秒、端末保存は約9msだった。
- Drive保存ジョブ約4.78秒、最後の編集から完了まで約7.43秒という観測がある。別の観測ではアップロード1回だけで約2.67秒かかった。
- PDF・操作・通信条件がそろっていない少数の記録なので、変更前後の改善率には使えない。11月9日以降の改善を含む現行コードの所要時間とも断定しない。
- CPU・画面の停止時間は既存ログでは測っていない。「通信が遅い」と「操作が重い」は分けて調べる必要がある。

## 既に実装されている改善

- 端末への確定保存とDriveへの背景送信の分離、連続編集の集約。
- 通常更新では編集JSONを送信し、元PDFを毎回アップロードしない。
- 小さいJSONの1リクエスト送信、Google算出チェックサムによる不要なJSON読み戻しの回避。
- アカウント・ルートの確認結果の30秒共有、保存前メタデータと親階層確認の並列実行。
- キャッシュ済み本文の先行表示、再取得時に照合できた元PDFのBlob再利用。
- 付箋索引の背景同期と取得処理の並列数制限。

これらを新しい高速化として再実装しない。

## 確認できた改善候補

| 候補 | コード上の根拠 | 想定する効果と注意点 |
| --- | --- | --- |
| 履歴検索・DB書き込みの削減 | `driveLibraryRemote.ts`の`fetchEvents`は履歴ごとに`cached.find`、終了時も`results.some`を使う。`arrange`は変更のないノートにも個別トランザクションで`parentId`を書き戻す | Map/Setによる検索、同値なら書き込みを省く処理、必要なDB操作の集約。ノート・履歴が増えたときの端末負荷を抑える候補。通信時間そのものは短くならない。トランザクション内で最新状態を再確認する |
| 階層同期内の独立した取得の並列化 | 現在は`fetchEvents`完了後に`arrange`から`listLibraryObjects`を開始する | 同一スコープの独立した読み取りを重ね、直列の通信待ちを減らす候補。履歴取得中の作成・移動で一覧の観測時点がずれる場合は採用せず再確認する。検証完了前に書き込まない |
| 本文送信前後の待ち順の整理 | `driveLibraryRuntime.ts`は30秒経過・未送信階層変更などで階層同期を待ってから`autosave.tick`へ進む。キャッシュ検証・整理も同じ実行ループで待つ | 一覧同期・保守処理が保存待ちへどれだけ影響しているか測定する。削除・移動・版採用の反映が本文送信に必要なので、単純に送信を先へ移す変更はしない |
| 編集中ノートの送信優先 | `driveAutosave.ts`はDBから得た候補を順番に送る | 大きい初回送信の後ろで編集中ノートが待つ状況を減らせる可能性がある。まず優先順を検討する。同時送信数を増やす場合は帯域・429・ロック・階層公開順序も検証する |
| JSON生成・一時コピーの削減 | `driveAutosaveRemote.ts`は容量確認・内容ハッシュ・最終送信データのためにJSONを生成する。`googleDriveClient.ts`の受信処理は各チャンクを`new Uint8Array(value)`でコピーする | 大きい書き込みデータのCPU負荷・一時メモリを減らせる可能性。内容ハッシュと送信全体のチェックサムは役割が異なるため統合しない。チャンク受信の実容量上限も維持する |

## バックグラウンド実行と操作感

`DriveAutosavePanel.tsx`は1秒ごとに送信判定、5秒ごとにDB由来の状態確認を行う。1秒ごとにDriveへ通信するという意味ではない。ランナーには重複実行防止・30秒の一覧更新間隔がある。

ただし、画面非表示時の不要な状態確認を減らす余地はある。未送信内容の保存を止めず、表示用確認・一覧更新・保守処理を分けて扱う必要がある。復帰時は再確認する。

JSON処理が入力を止めていることが確認できた場合、Web Workerへの移動も候補になる。Workerへ送る際の複製コストもあるため、先に計測し、通信待ちの解決策として導入しない。

## 公式仕様との照合

- [Driveの性能改善](https://developers.google.com/workspace/drive/api/guides/performance)：必要なフィールドだけの取得、独立したメタデータ要求のバッチ化を説明。現行コードは既に`fields`を指定している。バッチは最大100呼び出しで、実行順序は保証されず、メディアのアップロード・ダウンロードは対象外。現在の`Promise.all`より速いかは未測定。
- [アップロード方式](https://developers.google.com/workspace/drive/api/guides/manage-uploads)：小さいデータのmedia/multipartと、切断に備えるresumableを説明。現行コードは小さいJSONを1回で送っており、方式変更だけで大きく短縮できるとは考えない。
- [変更の取得](https://developers.google.com/workspace/drive/api/guides/manage-changes)、[changes.list](https://developers.google.com/workspace/drive/api/reference/rest/v3/changes/list)：ページトークンによる継続取得、削除・アクセス喪失の通知を扱える。`drive.file`も許可スコープに含まれる。対象は現在のアプリ権限で取得できる情報に限り、権限拡大は前提としない。
- [Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API)、[データ複製](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm)：メインスレッドと別に処理できるが、受け渡すデータの複製・転送も考慮する。

固定の「Driveなら何ms」という保証や、「CORSで必ず全通信が2倍になる」という前提は置かない。

## 実装前に追加したい計測

現在の`speedMeasurements.ts`には本文・階層・HTTP・接続確認などの計測がある。次は以下を分ける。

1. 階層同期の全件一覧取得・履歴照合・DB反映それぞれの時間と件数。
2. 本文が送信可能になってから実行開始までの待ち。既存の`queueWaitMs`と合わせ、階層処理や別ノート待ちを切り分ける。
3. JSON検証・文字列化・ハッシュ計算・送信サイズ。内容ハッシュと全体チェックサムは別々に計る。
4. キャッシュあり／なし／PDF再利用ありの表示、PDF解析・ページ描画。
5. ブラウザのPerformance記録で、編集・送信時の長いメインスレッド処理を確認する。

計測JSONには固定の処理名・時間・容量・件数だけを追加する。本文・ノート名・ファイルID・メール・トークンを含めない。

比較は同じPDF・同じ編集・同じブラウザ／URLで複数回行う。開発サーバーと公開環境は分ける。初回接続、初回取得、キャッシュ表示、通常更新、複数ノート待ちを混ぜず、中央値と遅い回、通信回数、エラーを残す。キャッシュなしの試験で利用者の既存データを削除しない。

## 推奨順序

1. 上記の不足する計測と、合成データによる大量ノート・履歴の検証を追加する。
2. Map/Set化、同値DB書き込みの省略など、保存形式を変えない処理削減を行う。
3. 独立した一覧取得の並列化と送信優先順を、別々に比較する。
4. それでも全件走査が支配的なら、差分取得を独立した単位で設計・実装する。
5. CPU負荷が確認された場合だけWorker化を検討する。

各単位で既存テスト・lint・型チェックと必要なビルドを確認する。削除後の復活防止、移動中の参照、競合、認証切れ、送信中の追記、キャンセル、通信失敗も検証する。短縮秒数は変更後の実測で判断する。
