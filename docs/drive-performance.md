# Drive接続時の速度改善

11月8日の利用者指定で、追加の速度調査・最適化と同条件での複数回比較は第7回へ繰り越す。実装済みの改善と現在の保存・競合保護は維持する。以下の実測・未確認事項は次回の調査資料として残し、第6回で速度改善完了とは扱わない。

## 実環境の速度計測（第6回・2026年11月8日）

Google Drive画面の「速度計測」を展開すると、開始・停止・結果保存・消去を操作できる。既定では無効。計測中にダイアログを閉じても継続するが、ページを再読み込みすると記録は消える。通常利用で自動送信する診断機能ではない。

1. 普段のURL・ブラウザで「Google Drive → 速度計測 → 計測を開始」を押し、画面を閉じる。
2. 雲マーク付きの未取得ノートを開く。続いて別のノートへ移り、先ほどのノートを開き直す。サイトデータを消して初回状態を作る必要はない。
3. テスト用ノートに線を描き、Driveの保存待ちが解消するまで待つ。未送信のままページを閉じない。
4. 再度「速度計測」を開き、「計測を停止 → 結果を保存」で `overlay-speed.json` を取り出す。別条件は新しく開始して記録する。

短い操作を2〜3回ずつ試し、初回と再表示を区別する。端末の種類、PDF容量・ページ数、回線、ローカル開発版／公開版の条件も併記すると比較しやすい。開発時の初回コンパイルを公開版と同じ条件として比較しない。11月8日にChrome開発版の実Google計測とリロード後の並列化を確認した（末尾参照）。同じ資料・操作で複数回の比較、スマホ・iPadの実測は未実施。

### 記録する範囲と読み方

- ノート選択からCanvas反映完了までの全体、切替前の端末保存待ち、取得・検証・端末読み込み、PDF.js準備、PDF解析、ページ描画を分ける。ファイル選択ダイアログの操作時間や物理ディスプレイの表示時間は含まない。`pdf.render` は100msの再描画待機後からで、全体の `note.open` には初回の描画待ちも含む。
- 端末への確定保存、Driveの送信準備〜結果反映、本文転送・検証、一覧・階層同期、付箋索引の背景同期を区別する。`queueWaitMs` は初回未送信編集からジョブ開始まで、`pendingMs` はその編集から保存結果反映まで、`sinceLastChangeMs` は送信した版の最後の編集から結果反映まで。再試行待ちや計測開始前の時間も含み得る。既定の2秒／最大10秒の待機設定を変更するものではない。
- HTTP記録はリクエスト開始から応答受信まで。`headersMs` は応答ヘッダー取得まで、`bodyMs` はその後の受信・JSON解析等。通信先URL・ファイルID・送受信本文は記録しない。ブラウザのCORS待ちを含む可能性はあるが、OPTIONSを個別に数える計測ではない。
- 親子の処理や並行通信、背景同期は時間が重なる。所要時間をすべて足して待ち時間と解釈しない。`parentId` はこの計測内だけの連番で、ノートやDriveのIDではない。通信数やファイルサイズの違いと合わせて比較する。
- 成功以外は `error`、切替等の中断は `cancelled`、版の選択待ちは `choice`、停止時に継続中なら `incomplete` とする。成功の平均値に混ぜない。

記録は端末メモリ内の直近1000件・実行中100件までで、上限超過を画面とJSONへ記載する。開始・消去でリセットする。PDF本文、ノート名、ファイル名、アカウント、認証情報、URL、例外本文、生のUser-Agentは保存せず、時間・数値・許可した区分だけを保持する。ブラウザ区分、開発／本番、画面寸法と画素比は書き出し時に付ける。DB・Driveへの追加保存、追加API、先読み、保存方式の変更は行わない。

`speedMeasurements.ts` が記録上限・許可項目と計測セッションを管理し、`SpeedMeasurementPanel.tsx` が操作とローカルJSON出力を担当する。記録停止・開始をまたぐ遅い応答は次のセッションへ混入させない。テストは仮時計・仮API・代用Canvasで検証し、計測を有効にしても保存結果・例外・通信回数が変わらないことを確認する。

容量は初期250MB・100〜1,000MBの設定、保持は未使用30分。保護条件と操作は[Drive設計](drive-storage.md)を参照する。

2026年11月5日。通常の同時編集は主用途としないが、端末の使い分け・古いタブ・外部変更による競合は考慮する。競合保護を外して高速化する方針ではない。

## 変更内容

- 取得済みの単一版は、通常のノート選択でGoogle通信を待たずに開く。裏で編集JSONのメタデータを確認し、同じ版の確認は30秒以内に繰り返さない。未取得・複数版の選択・明示的な再取得・バックアップは従来の検証を維持する。
- 裏の確認でDriveの更新を検出したら、表示中の本文・PDF・更新番号を変えず案内する。次の再選択で取得を検討し、未送信の変更や自端末保存先の想定外の変更があれば保護して停止する。通信失敗でも端末の内容を残す。別ノートへ切り替えた後の警告を現在の資料へ表示しない。
- 自動保存は従来どおり端末別の保存先を使用する。送信前後の所有者・参照・更新番号・内容ハッシュ・PDFチェックサムの検証は省略しない。別端末の本文を自動で統合しない。
- 再取得可能キャッシュの保持を未使用30秒から30分へ延長する。長く開いたノートは閉じた時点から数える。設定した容量を超える場合は古いものから整理する。未送信・保存失敗・編集中・他タブ使用中・ローカル専用は従来どおり保護する。30分は永続保存の保証ではない。
- 接続先アカウント・専用Overlayルートの完了済み確認結果は、同じ認可オブジェクト・トークン・アカウント・ルートに限り、別クライアント間でも30秒再利用する。明示的な接続確認では再取得し、認可変更・失効・キャンセルで破棄する。本文・PDFの検証は別に維持する。
- 送信判定の1秒間隔は維持し、UIの状態取得は変更通知と別タブを確認する5秒間隔へ分離する。待機中は階層全件を読まず小さな送信待ちフラグを確認し、キャッシュ整理は30秒間隔とする。変更のない階層同期では全ノート本文の取得・再保存を行わない。

DB版7、Driveのファイル形式・フォルダ構成は維持する。元PDF・編集本文を別ストアへ重複コピーしない。既存ノートの再取り込みやサイトデータの削除は不要。

## 初回取得の並行化（2026年11月5日・追加改善）

`googleDriveNotes.ts`の読み取りを次の順序へ変更した。

1. ノートのメタデータで所有者・目印・識別子とJSONサイズ上限を確認する。`driveLibraryCache.ts`ですでに取得した情報は、この操作内でだけ共有する。
2. 保存フォルダからOverlayルートまでの階層検証と、編集JSONの取得・検証およびPDFメタデータ取得を並行する。JSONは16MiB上限で、PDF本文はまだ取得しない。
3. 両方の検証成功後、PDF本文取得とノートの版確認を並行する。所有者・参照・端末・更新番号の変化を拒否し、PDFサイズ・形式・チェックサム・ページ参照も確認する。
4. 既存の端末側の更新検出を通過してから、PDFと編集内容を同じトランザクションで保存する。失敗時は既存データを上書きしない。

版確認を削除せず、早期の同じメタデータの二重取得から、後段の変更検出へ移した。通常の未取得ノートの通信は9回のまま。階層が無効な場合に小さなJSONの読み取りが先行することはあるが、PDF本文取得・表示・DB書き込みは行わない。読み取りだけを並行し、保存・削除の順序は変更しない。

| --- | --- | --- |
| キャッシュなし | 約1365ms・9通信 | 約912ms・9通信（約33%短縮） |
| キャッシュあり | 約1ms・表示前0通信 | 約1ms・表示前0通信 |

認証・実ネットワーク・PDF画面描画は含まない。階層の深さ、ファイルサイズ、Google側の応答時間で効果は変わる。大規模ライブラリの履歴走査や送信方式はこの単位では変更していない。

## 第6回：送信JSONの読み戻し削減（2026年11月6日）

通常の自動保存は、フォルダ・PDF・JSONのメタデータ3件を並行取得した後、旧JSONをダウンロードして検証し、JSONを更新してもう一度ダウンロードしていた。版番号のみの差ではなく、Googleのsha256Checksumと送信済みの全バイトSHA-256・サイズの一致を使う。

- 送信前：既知の送信済みJSONと全バイトが一致すると確認できる場合、読み戻しを省く。応答消失後に今回送るデータと既に一致していれば、重複送信せず完了を確認できる。
- 送信後：アップロード応答だけで完了にせず、JSONファイルのメタデータを別途取得して内容チェックサム・サイズを照合する。所有者・保存場所・端末・IDの検証も維持する。
- 不一致・未提供・旧情報：従来どおりJSONを取得し、形式・参照・世代・再計算した内容ハッシュを検証する。未提供時は送信後のメタデータ確認が増えるため、従来より1通信多くなる場合がある。
- IndexedDBの送信情報にuploadedChecksumとuploadedJsonBytesを追加。本文の複製や新ストアは作らず、DB版7・Drive JSON形式は変更しない。送信中の追記と新しい送信済み情報を古い完了結果で巻き戻さない。
- 自端末の保存先の版番号だけが変わった場合も、同じチェックサム・サイズがあればJSONを取得せず同一内容を確認する。旧保存情報では本文検証へ戻る。

Googleが返すチェックサムの意味は[Files仕様](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)に基づく。未知の内容を名前・同一端末・版番号だけで安全とみなす方式へ変更しない。

同じ仮APIとテスト入力、各通信50ms。すでに初回保存済みのノートへ、20,000点の線を追加し、429,267バイトの編集JSONを送る1回の比較：

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| リクエスト数（メタデータ3件は並行） | 6 | 5 |
| 確認用JSONダウンロード | 2回・計429,664バイト | 0回・0バイト |
| runner.tickの計測例 | 約244ms | 約180ms |

計測はtests/drive-autosave.test.tsの「仮APIで通常更新」で再現できる。時間は環境負荷で変わるため合否基準にしない。合否は通信数・JSON取得回数・保存結果で判断する。認可・共通階層同期・実Google・PDF描画・2秒の送信待機は含めず、実環境の短縮率を保証しない。

JSONの1回送信の上限は1MiBから4MiBへ拡張した。multipartのメタデータ分も含めGoogleの小さいファイル向け5MBを下回る範囲を使用する。元PDFと4MiB超JSONのresumable方式は維持し、1〜4MiBと4MiB超の読み戻し・認可失効・通信断・再開URL検証を確認した。[Googleの送信方式](https://developers.google.com/workspace/drive/api/guides/manage-uploads)

受信のboundedBlobは変更していない。Content-Lengthだけを信じず受信中にも容量を制限する処理を残す。受信コピー削減・圧縮・差分形式・大規模階層の索引変更は、実測後に別途検討する。全594テスト・lint・型チェック成功。本番ビルドは隔離コピーで確認。実Google・公開環境・iPadの確認は未実施。

## 本文採用後の再表示（2026年11月8日）

採用済みで候補が1つ、取得済み本文・PDFが一致し警告がない場合は、従来の単一版と同様にGoogle通信を待たずキャッシュを表示する。裏の確認で各保存先の版・チェックサムを検証し、旧版への新しい編集・別の採用があれば現在の本文を保ったまま案内する。採用が未解決の時は候補のメタデータを最大4並列で取得し、実体を読む前後にも選択が古くなっていないか確認する。

約30秒の背景索引取得で既に集める本文メタデータを再利用し、採用版の候補と付箋一覧も更新する。本文自動保存の通常周期に、採用済み全ノートの個別メタデータ取得を追加しない。初回の採用・旧版の確認には通信時間が必要であり、実Googleでの短縮時間は未計測。


## Drive画面の一覧取得を分離（2026年11月8日）

通常のGoogle Drive設定には接続先だけを表示し、手動保存・復元の一覧を置かない。通常のノート一覧がクラウド資料の表示・必要時取得を担当する。以前の手動保存分の復元は「バックアップを読み込む → 以前のDriveバックアップから」へ分離し、その画面を開いた時だけlistNotesを呼ぶ。明示的な更新・次ページ取得は維持する。手動保存もノート操作／複数選択からの専用確認へ分離する。

- `googleDriveClient.ts`：同じ認可オブジェクトをキーに、完了済みのアカウント・ルート確認をメモリ内で最大30秒共有する。自動保存・階層同期の初回アカウント確認だけ共有を許可し、通常の `getAccount()` と明示的な `findRoot()` はAPIで再確認する。利用するたびに期限を延長しない。トークン変更・失効通知・401・キャンセルで破棄し、古い通信結果で共有結果を復活させない。

- PDF・JSONの所有者、保存位置、参照、チェックサム、競合と送信後の実体再確認は省略しない。元PDFのBlob再利用、早期ダウンロード、保存待機時間・容量上限・保存形式の変更は今回含めない。

## 検証済みPDFの再利用と計測の補足（第7回・2026年11月9日）

`googleDriveNotes.ts`と`driveLibraryCache.ts`で、再取得時に元PDFが同じならIndexedDBの既存Blobを再利用する。今回の通信で所有者・保存先・PDFメタデータ・編集JSONを検証した後、Google算出の64桁SHA-256があり、Blob容量と実際に計算したSHA-256が一致する場合だけPDF本体の転送を省く。端末に保存したハッシュ値だけを信用する方式ではない。

PDFが未取得・整理済み・不一致、またはGoogleのチェックサムがない場合は従来の容量制限付き取得へ進む。取得後のPDF形式・容量・ハッシュ・ページ対応と、並行して確認するノートの最終版、DB反映前のアカウント・参照・未送信保護は維持する。PDF／ハッシュの新しい永続キャッシュは増やさない。通常のキャッシュ表示は従来どおりHTTPなし。削減対象はキャッシュのある資料の再取得時のPDF転送1回であり、初回取得・編集JSONの更新・保存前のPDFメタデータ確認は省略しない。

速度計測を開始した時だけ、`drive.pdf`に`pdfReused`（真偽値）とPDF容量を記録する。`drive.connection`の`connectionCheck`は以下の固定値だけを記録し、アカウント・保存先ID・トークンは出力しない。

| 値 | 意味 |
| --- | --- |
| `account-hit` / `root-hit` | 30秒以内の確認結果を再利用 |
| `account-missing` / `root-missing` | 共有結果がないため確認 |
| `account-expired` / `root-expired` | 確認結果の期限が過ぎたため確認 |
| `root-mismatch` | アカウント／保存先が共有結果と異なる |
| `account-explicit` / `root-explicit` | 明示的な再確認 |

30秒の上限や破棄条件は変えない。通常の`getAccount()`は共有結果を破棄し、明示確認・認可変更・失効・キャンセル等の後は再確認する。前回ログで確認通信が残った直接の理由は、この追加項目のある実測で確認する必要がある。今回のコード調査だけで前回の実行理由を断定しない。
