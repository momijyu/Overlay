# Google Driveへの手動保存・コピー読み込み

2026年11月5日の更新：利用者が選んだ最初の段階として、端末・ノートごとに保存先を分けるDrive自動保存を追加。明示的に有効化したノートだけを対象に、未送信情報をDB版6へ保持し、予約IDで再試行します。JSON版4（sync-note）は手動上書きと分離し、各端末の版を一覧からコピーして選べます。既存ノートの全件送信・自動統合は行いません。500MB整理・Driveのみを本体とする読み込み・階層同期は後続で、送信済みローカル本文・PDFも保持します。[操作と制約](./drive-autosave.md)。以下の未実装等の記述は先行段階の経緯として読み、現在の状況はこの追記を優先してください。

2026年11月4日の続く指示で、選択した複数ノートの一括保存を追加した。同名がなければ新規保存、1件あれば確認後に上書きする。Driveを通常の自動保存先へ切り替える段階ではない。Drive正式保存・未送信保護・競合対策・500MBキャッシュ整理の方針は[保存計画](./drive-storage-plan.md)を参照する。

## 操作

1. 編集中の文章は「完了」などで確定する。ノート一覧の「選択」で保存したいノートをチェックして「Driveに保存」を押す。フォルダ選択でチェックされた子ノートも対象。空フォルダだけでは保存できず、階層や空フォルダ自体はDriveへ複製しない。1回1〜200件。単独なら「操作 → Google Driveに保存」も使える。未表示のノートも保存できる。
2. 有効な接続がなければGoogleで接続確認する。接続済みなら同じページ内では認証を繰り返さない。保存先の取り違えを防ぐため、メールアドレスは表示し、氏名は表示しない。
3. 選択した全ノート名と「新規」「上書き」が一覧に出る。通常の「Google Driveの接続確認」から開いた場合は「開いているノートを保存」で現在の確定内容を取得する。
4. 一括確認の「まとめて保存」、上書き対象があれば注意を確認して「上書きを含めて保存」を押す。単独操作メニュー経由は従来の「保存」「上書き保存」。「キャンセル」では書き込まない。同名がDriveに複数・検索が未完了の場合は自動で選ばず停止する。選択したローカルノート同士が同名の場合も、名前を変更するまで保存しない。検索対象は本人のOverlay専用ルートに属する、アプリが作成した編集JSONだけ。
5. 成功表示と一覧の対象名を確認する。検証済みの保存応答から直ちに反映し、全件の再検索は待たない。最新のDrive側の状態は「更新」で取得する。
6. 一覧の「ブラウザへコピー」を押す。ダウンロード・形式検証後に既存の復元確認画面へ移る。承認後、同じ元PDF・書き込みのノートが既にあれば追加せず案内する。内容が違えば新しいローカルIDで一覧へ追加する。キャンセルではコピーしない。
7. 追加されたノートを一覧から開き、手書き・文章・色を確認して再編集する。編集の自動保存先はこのブラウザで、Driveへは自動反映しない。

接続確認だけではノートを送らない。現在開いているノートは操作時点の未保存の確定編集も含める。ほかのノートは実際の送信時にIndexedDBから1件ずつ読む。確認後に名前が変わっていれば送信を止める。元のローカルノート・履歴は変更しない。Driveの削除・フォルダ整理は今回含めない。

## 一括保存の進行と中断

`googleDriveBatch.ts`は名前・ID・取得口と小さな進行状態だけを保持する。保存先の事前確認ではPDFや編集JSON本文を読まず、同名候補を検索する。全対象が確認できてから一括の確定操作を受け付け、元PDF・編集本文の取得と送信を1件ずつ直列に実行する。全件のPDFをまとめて読み込んだりZIP化したりしない。今回の上限は200件で、1件ごとのPDF256MiB・編集JSON16MiBの上限は維持する。

保存中は各ノートの「保存中…」「保存済み」を表示し、失敗したら後続を送らず停止する。「保存済み」「要確認」「未処理の新規／上書き」と保存済み・残りの件数が確認できる。成功したDrive保存は取り消さず、結果不明の項目は自動再送しない。Drive側の一覧を確認したうえで「残りの保存先を確認」を押すと、成功済みを除いて候補と版を取得し直す。再度の一括確認後に残りだけ送信する。成功済みは同じ確認画面内では再検索・再送しない。

外側の「閉じる」で送信を中断できる。送信済みはDriveへ残り、送信中だった項目は結果不明になる場合がある。閉鎖・再読み込み・アカウント選び直し後の進行状態の永続復元や自動再開は行わない。開き直したらDrive一覧と対象を確認し直す。各ファイルを別々に送るため、全件まとめての原子的保存・ロールバックではない。

## 接続の再利用と上書きの制約

`googleDriveSession.ts`が同じページ内の有効な接続をメモリだけに保持する。閉じると進行中の通信・操作を中断し、次のAPI操作は改めて保存場所を検証する。トークン・接続アカウントをDBやlocalStorageへ保存しない。ページ再読み込み・期限切れ・失効後は再接続する。「アカウントを選び直す」は明示的にGoogle認証を行う。[GIS token model](https://developers.google.com/identity/oauth2/web/guides/use-token-model)の方式のため、バックグラウンドで期限を無制限に延長するものではない。

同名の上書きでは、対象の所有者・コンテナ・形式・JSONとPDFの参照を検証し、確認時と保存直前のJSONの`version`を比較する。再利用するPDFも版とチェックサムを再検証する。変更が見つかれば上書きせず、キャンセルして確認し直すよう案内する。ただし最後の確認と更新の間は原子的ではなく、別端末の同時保存を完全には防げない。確認画面に「他の端末と同時に保存しないでください」と表示し、この方式を自動同期へ流用しない。競合を確実に保護する正式保存の仕組みは後続。

Driveの元PDFのサイズと[出力専用のSHA-256チェックサム](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)が一致すればPDFを再送せず、編集JSONだけを[files.update](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update)で更新する。比較時は送信元PDF1件分の一時ArrayBufferを作るため、最大256MiB程度に加えブラウザ処理用メモリが必要になる。比較用ハッシュやPDFをDBへ追加保存しない。チェックサムが取得できない・不一致の場合は新しいPDFを送り、最後のJSON更新で参照を切り替える。古いPDF・途中失敗したPDFは自動削除しないため、その場合はDrive容量が増える。

閉じると旧操作番号を失効させるため、通信のないPDF照合中に閉じても後から送信を再開しない。更新済み応答が届く前に閉じたり通信が切れたりした場合、Drive側では保存済みの可能性がある。自動再送せず一覧を更新して確認する。

## 重複と端末内の容量

Driveからの復元では、名前・所属・IDではなく、元PDFの全バイトと検証済みの線・文章で比較する。空ページ配列の有無は差にしない。文章のIDや位置・色・太さなどが異なる場合は、安全側に別内容として扱う。同じPDFでも編集が違えばコピーを追加し、元のローカルノートを上書きしない。既存の重複をまとめて削除する処理は追加していない。`.overlay`・ZIPファイルからの通常バックアップ復元は従来どおりコピーを追加する。

`noteDuplicates.ts`は一覧のIDだけ取得し、本文を1件ずつ確認する。編集情報が一致する候補だけPDFを1MiBずつ読み比べ、全PDFをメモリへ並べず、比較用データもDBへ保存しない。Blob比較はトランザクション外、比較結果の再検証と復元は同じ書き込みトランザクション内で行う。別タブの追加・編集・削除で結果が古くなれば中止して再試行を案内する。Drive復元前には現在の自動保存を待つ。

この段階ではコピーしたPDF・編集情報はIndexedDBの通常ノートとして残る。同じ内容の繰り返し復元は増えなくなるが、異なるノートや編集版を追加すると使用量は増える。500MBの自動キャッシュ整理は未実装で、Drive正式保存への切り替え・未送信保護と合わせて後続で接続する。保存先の切り替え前にローカルデータをキャッシュとして消さない。

現在は毎回、所有者・保存場所の確認、JSONとPDFの取得・検証を行う。重複判定もダウンロード後の復元時に行うため、今回の変更は通信の短縮ではない。所要時間の内訳は未計測であり、即時読み込みや一定秒数での完了は保証しない。

## 先行した新規保存の通信削減

続く最適化で、1MiB以下の編集JSONは[Google公式のmultipart方式](https://developers.google.com/workspace/drive/api/guides/manage-uploads#perform_a_multipart_upload)でメタデータと本文を1回で送るよう変更した。大きいJSONと元PDFはresumable方式を維持する。JSON送信は元PDFの成功後だけ行い、応答を失っても自動で再作成せず、一覧の更新で確認する。Drive側のファイル構成・形式版は変えない。

保存が成功したら検証済みの応答を一覧先頭へ反映し、専用ルートの再検索と一覧取得を追加で待たない。一覧にはID・名前等の小さな情報だけを保持し、PDF・JSON本文を追加キャッシュしない。既存項目と続き情報は保持し、他端末の変更は「更新」で取得する。

同名確認の追加前は、確認済み画面の保存から反映まで8回だった通信を、小さいJSONで5回・大きいJSONで6回へ減らした。現在の画面経路は別途同名検索・上書き対象の検証があるため、5回を一連の操作全体の上限とは扱わない。保存先確認と一覧を同時に取得する際は、実行中のルート検索だけを共有する。OAuth・初回接続・CORS事前通信や再試行は別。実Googleの時間短縮率は未計測。読み込み時の再取得抑制は500MBキャッシュ等との接続が必要で、まだ実装していない。

## Drive内の形式

```text
Overlay/                        アプリ専用のルート
  ノート名/                     新規保存時に作成、上書きは同じコンテナ
    元ファイル名.pdf            元のPDFをそのまま保存
    ノート名.overlay.json       編集用のJSON
```

見出し付きJSONは`schemaVersion:3`で、`headingsByPage`にページIDと見出しを保持する。ページ構成の有無にかかわらず扱い、旧版1・2も読み込む。見出しだけの変更・削除は元PDFが同一ならJSONだけ更新する。単体・一括手動保存とコピー復元で保持する。閲覧用PDFへ印字する情報ではない。[ページ見出し](./page-headings.md)。

JSONは旧ノートが`schemaVersion: 1`、ページ構成付きが`schemaVersion: 2`で、後者は`pages`にページID・表示順・白紙寸法を含める。両方を読み込める。その他の項目は`kind: overlay-drive-note`、ノート固有キー、名前、元ファイル名、PDFのDrive IDとサイズ、`strokesByPage`、`textsByPage`を持つ。トークン・クライアントシークレット・ダウンロードURLは記録しない。フォルダ／PDF／JSONの`appProperties`へOverlayの目印、形式版、役割、ルートID、ノートキーを付ける。表示名だけで別のファイルを読み込まない。

元PDFを先に送り、最後に編集JSONを送る。JSONのアップロードが完了したものだけを一覧の対象にする。Drive側に複数ファイルを原子的に書く機能があるとは扱わない。途中失敗でノートフォルダ・PDFが残る場合があり、自動削除はまだ行わない。保存結果が不明なら勝手に同じ送信を繰り返さず、一覧の更新で確認する。

## 処理と検証

- `googleDriveNoteData.ts`：形式とID、所有者、保存場所、アプリの目印、一覧情報、編集JSONを検証。線・文章の検証は既存の`noteBackupData.ts`と共用する。
- `googleDriveNotes.ts`：新規コンテナ、元PDF、編集JSONの順で保存。同名確認・手動上書き・PDF照合を担当する。一覧は50件単位のメタデータだけを読み、選んだノートの本文・PDFだけをダウンロードする。
- `googleDriveClient.ts`：各操作を確認済みアカウント・専用ルートへ固定する。固定Google APIへ認証ヘッダーを送り、resumableの送信先URLもGoogleの所定パスだけに制限する。受信本文をサイズ上限で止め、失効・アカウント変更・閉鎖後は結果を採用しない。
- `GoogleDriveNotes.tsx`：保存対象の確認・キャンセル、送信状態、一覧の更新／追加取得、コピー読み込みを表示する。読み込み中に閉じても、後から復元画面を開かない。
- `googleDriveBatch.ts`・`GoogleDriveBatchSave.tsx`：一括の対象確認、新規／上書き表示、直列送信、途中失敗時の成功分保持・残りの再確認を担当する。
- `PdfWorkspace.tsx`：最新の確定済み編集を保存スナップショットへ渡す。Driveから読んだ内容は既存の復元確認へ渡し、承認前にDBへ書かず、開いているノートも置き換えない。

元PDF・大きいJSONは[Google公式のresumable方式](https://developers.google.com/workspace/drive/api/guides/manage-uploads)で初期化し、続くPUTでBlobを送る。1MiB以下のJSONは上記のmultipartを使う。今回は送信中の中断からの自動再開・バックグラウンド再送・終了後の送信継続は実装しない。ノート本文は[files.getのalt=media](https://developers.google.com/workspace/drive/api/guides/manage-downloads)で取得する。

この単位の上限は1ノートの元PDFが256MiB以下、編集JSONが16MiB以下。既存の復元用検証の安全上限に合わせたもので、500MBキャッシュやIndexedDB全体の上限とは別。ブラウザの使用メモリをこの値以下に保証するものではない。対応する別アカウントの承認・利用はGoogle側のテストユーザーや組織ポリシーにも依存する。

## 状況

Chrome・localhost:3000の新規保存・一覧表示はユーザー画像で確認済み。コピーに続き、一括保存の使用もできていそうとの利用者報告を受けた。手動保存・コピー読み込み・一括保存の基本機能を一区切りとし、Drive関連UIの配置・文言・進行表示の調整は後続へ保留する。失敗・中断・再接続・コピー重複防止、他端末・スマホ／iPad・公開環境の全ケースは網羅確認していない。自動テストは代用fetch・hooksと隔離したローカルDBのみで、実Googleへの書き込みや利用者の保存データは操作していない。

実機では不要なテスト用ノートで「一覧のノート1件選択 → Drive保存 → 閉じる → 認証なしで再表示 → 編集後の同名上書き確認 → コピー確認 → 復元 → 再編集 → 開き直し → PDF出力」を確認する。上書きキャンセル・期限切れ時の再接続・別ブラウザからの取得も確認する。保存結果が不明な場合はまず一覧を更新する。

空白ページは元PDFへ焼き込まず編集JSONで管理する。同じPDFを使った白紙追加の上書きでも、チェックサムが一致すればPDFを再送しない。コピー復元の重複判定は白紙の位置・サイズも比較する。[空白ページの詳細](./blank-pages.md)。
