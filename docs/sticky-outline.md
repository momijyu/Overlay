# 付箋一覧から資料・ページを開く

## 操作

1. PDFへ付箋を書き、内容を確定する。
2. 左上の三本線メニューから「付箋一覧」を展開する。
3. 資料名ごとに並ぶ「ページ番号・付箋の先頭行」を押す。
4. 該当資料のページを開く。メニューは開いたままなので、必要な時に閉じる。

すべての付箋が自動で載る。付箋ごとの登録・見出しの再入力は不要。テキストボックスは対象外。同じページに複数の付箋があれば各行として並ぶ。先頭の空行は飛ばし、最初の内容のある行を最大120文字まで表示する。

このブラウザに保存した資料と、接続したDriveの共通一覧にある資料を対象とする。開いている資料は未保存の確定内容も優先し、未保存の新規資料も表示する。資料内は現在の表示ページ順で、白紙にも対応する。独立したページ見出しUIは廃止済みで、旧データのみ互換性のため保持する。

## 移動と編集の連動

移動先はノートID・安定したページID・付箋IDで確認する。白紙を挿入してページ番号が変わっても元のページへ戻れる。付箋の位置を変えても、その付箋のあるページを開く。位置までの自動スクロールや強調表示は今回含めず、移動単位はページ。

同じ資料内の移動ではPDFの再取得・履歴のリセット・新しい保存は行わない。別資料を開く前は今の自動保存を待ち、失敗時は既存の破棄確認を通す。キャンセルや読込失敗では元の資料と履歴を残す。古い一覧から削除済みの付箋を選んだ場合も切り替えず、一覧の更新を案内する。

付箋の作成・変更・削除・Undo / Redoへ連動する。開いている資料は画面の確定済みデータを使うため、保存待ち・保存失敗時も古い一覧へ巻き戻さない。草稿は確定前なので一覧へ反映しない。ほかのタブによる変更はメニュー内の「更新」で読み直す。

## 保存と容量

付箋の本文・位置・IDは従来の`textsByPage`を使う。利用者用URL・付箋を登録するフラグは作らない。元PDF・編集JSON・バックアップの形式は維持し、Driveに一覧専用の付箋索引を追加する。バックアップ復元時は編集本文から一覧を再生成する。

一覧専用ストア`noteSummaries`に`stickyNotes`としてページID・付箋ID・表示番号・先頭行だけを追加する。PDF・線・座標・付箋の全文は含めない。通常の保存・名前変更・移動・削除・復元で、本文と同じトランザクションで更新する。付箋がなくなれば参照もなくなる。

現行IndexedDBは版7。この付箋参照は版5で追加し、その移行時だけ既存本文をカーソルで1件ずつ読んで生成する。全本文の一括取得はせず、PDF・編集本文・見出し・更新番号は変更しない。移行が失敗したら版更新ごと取り消す。以降の一覧表示は一覧専用情報だけを読み、全本文・PDFは取得しない。初回の時間・派生一覧の容量は資料数と付箋数に応じて増える。

古いタブは閉じて更新版を開く。サイトデータ削除やDBの初期化は不要。Drive自動保存・キャッシュ整理の現行仕様は[Drive設計](drive-storage.md)を参照する。

## Driveの未取得資料の付箋

ノート名・階層は既存の管理履歴、付箋は端末別保存先ごとの `.overlay-stickies-保存先ID.json` から取得する。索引はOverlay直下へ固定IDで作成し、改名・フォルダ移動で複製しない。先頭行120文字・安定ページID・表示番号・付箋ID、論理ノートID・端末別本文ID・世代を保持する。PDF・線・座標・全文は含めない。

- 本文がDriveへ確認済みで、端末の世代と送信済み世代が一致する場合だけ索引へ公開する。約30秒ごとの一覧確認に合わせ、通常の階層・本文処理とは別の背景タスクとWeb Lockで送受信する。本文を保存できたことと、付箋一覧が別端末へ反映済みであることは区別する。
- 付箋の追加・先頭行変更・削除・白紙挿入による表示番号変更は索引を更新する。位置・色・ペンのみの変更で索引を再送しない。階層の不変履歴を付箋編集ごとに増やさない。
- 一覧確認では索引と旧形式の本文メタデータをページ分割して取得し、チェックサムが変わった索引だけを最大4並列で読む。索引がない旧資料は、1周期4件まで編集JSONを取得・検証して一覧参照を生成する。PDF本体は取得せず、生成した参照を端末へ保持して同じチェックサムの本文を読み直さない。旧資料が多い場合は複数周期かかる。
- 複数版がある資料は保存先IDを付箋の移動先にも持ち、一覧で「版1」「版2」を添える。本文の採用後は採用版とその続きの索引だけを通常の一覧へ載せる。未確認の変更・分岐があれば該当版も候補へ戻す。押した版を取得した後でページ・付箋の実在を確認する。編集中の資料は従来通り画面の確定済み内容を優先する。
- 一覧の削除履歴を優先し、Driveへ索引が残っていても削除済み資料は表示しない。未送信・取得済みの編集本文を、遅れて取得した索引で上書きしない。複数版の一覧を自分の版の索引へ混ぜて送信しない。
- 未取得資料が残る間は「付箋はありません」と断定せず、未取得の案内を出す。索引の失敗時は既存の一覧を保持し、本文の自動保存を継続する。定期確認または「Drive一覧を更新・再試行」でやり直せる。
- 新規索引IDは送信前に端末へ予約・保存する。作成／更新の応答消失時は同じIDと確認済み内容で再試行する。所有者・保存場所・参照・世代・実際のSHA-256とサイズを検証し、重複や想定外の改変では索引の更新を止める。旧本文から生成した参照と同じ内容なら、ペン更新による世代差は競合としない。

索引は1保存先につき最大1万件・8MiB、一覧メタデータは最大2万ファイル。派生一覧なのでPDFキャッシュと同じ容量整理では消さず、データ量はノート数・付箋数に応じて増える。IndexedDB版7の既存ストアへ省略可能な項目を追加し、DB初期化はしない。手動バックアップだけで共通階層へ未登録のノートは対象外で、通常の「ブラウザへコピー」後は従来通り一覧に載る。

## コードの役割

- `stickyOutline.ts`：付箋の抽出、先頭行・表示ページ番号の生成、現在資料の差し替え、最新IDによる移動先確認。
- `localNoteSummary.ts`・`localDatabase.ts`：小さな一覧参照の生成・版5移行。通常更新は既存の`localNotes.ts`のトランザクションを利用する。
- `driveStickyIndexData.ts`・`driveStickyIndexRemote.ts`・`driveStickyIndexLocal.ts`：Drive付箋索引の検証・送受信・旧本文からの生成と、未取得資料の一覧参照更新。
- `components/StickyNotesPanel.tsx`・`NotebookSidebar.tsx`：資料・保存先別の付箋一覧と移動操作。描画自体は小さな一覧参照だけを使う。
- `components/PdfWorkspace.tsx`：現在資料のページ移動、別資料を保存待ち後に開く操作と、古い参照の拒否。

自動確認は隔離DBと代用イベントで行う。実ブラウザの保存データ・実Google Driveは変更しない。Chrome・スマホ・iPad・公開環境での通し確認は未完了。
