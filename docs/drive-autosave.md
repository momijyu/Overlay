# Drive自動保存（最初の段階）

最新の操作（2026年11月5日）：Googleアカウント・Overlayフォルダへの接続確認後、全ノート・フォルダの自動保存を開始する。個別の有効化・連携開始操作は不要。未接続・失効中は端末へ保管し、同じアカウントへの再接続後に再開する。以下の個別設定手順は過去の段階の記録。

## 2026年11月5日の続く実装（最新）

利用者の開始指示により、フォルダ構造をDriveへ連携する単位を追加。名前・パスでなく固定IDで移動し、同時変更は履歴の分岐として検出する。名前・配置の競合は選択後の合流履歴で解決し、本文は端末別に保護する。別端末では一覧だけ取得し、開く時だけ選んだ版のPDF・編集内容を取得する。全ノートの自動保存対象化、送信確認後の未使用キャッシュ整理（500MB上限・原則30秒）、追加PDFの選択フォルダへの初回保存、削除の他端末への反映も接続。DB版7は既存データと送信待ちを保持する。アカウント変更・削除や欠落時に勝手な再作成・転送を行わない。実Google・iPad・公開環境・速度の通し確認は未実施。詳細と制約は[Drive階層連携](./drive-library.md)を参照。以下の「階層同期・キャッシュ整理は未実装」は先行段階の記録。

2026年11月5日の利用者回答「端末ごとに分けて内容を保護する」を反映。全端末が同じJSONを上書きする方式にはしない。既存の手動保存・コピー読み込みは残す。

## 初期段階の操作（現在は接続後に自動開始）

1. ノート一覧の「Google Driveの接続確認」でアカウントとOverlayフォルダを確認する。
2. 保存済みのノートを開き、一覧内の「Drive自動保存 → このノートで有効にする」を押す。PDFを開いただけで未保存の場合は、最初の書き込みを確定してから設定する。
3. 以降の確定した編集を端末へ保存し、通常は最後の編集から2秒後（最大10秒待ち、確認タイマー分の約1秒と送信時間は別）にDriveへ送る。元PDFは初回だけ送信し、通常更新は編集JSONだけ送信する。
4. 一覧を閉じても画面が動作していれば送信を続ける。「一時停止」は以後の送信を止めるが、送信中の1件は完了する場合がある。再有効化では同じ保存先を使う。
5. 通信断は2〜60秒の待機を増やしながら再試行する。期限切れ・再読み込み後は「Google Driveの接続確認」から再接続する。権限エラー・競合などは停止し、「再試行」を明示的に押す。
6. 別端末ではDrive一覧の端末番号・更新日時を確認し、「ブラウザへコピー」から必要な版を読み込む。その端末でも自動保存を有効にすると、別の保存先を作る。異なる編集は別ノートとして保持し、自動統合・自動選択はしない。

有効にしていないノートは従来のブラウザ内保存。接続しただけで既存ノートを全件送らない。初回有効化では元PDF・編集情報を本人のDriveへ送る。画面の外側には未送信・停止時だけ短い案内を出し、送信完了の常設表示は出さない。

## 保存形式と保護

```text
Overlay/
  ノート名 (端末番号)/        ノート・ブラウザごとに独立した保存先
    元ファイル名.pdf          元PDF、以降の通常編集では変更しない
    ノート名.overlay.json     schemaVersion:4、sync-noteという専用の目印
```

JSONは線・マーカー・テキスト・付箋・白紙と表示順・見出しを含む。元PDFへ焼き込まない。ノート名変更はJSONの名前・内容に反映するが、コンテナ名は作成時のまま。ローカルのフォルダ階層の同期は今回含めない。

自動保存JSONの専用の目印を従来の手動保存と分け、手動上書きの対象から外す。従来のJSON版1〜3も読み込める。端末・保存先・所有者・PDF参照・サイズ・世代・内容ハッシュを検証し、想定外の変更があれば止める。別端末同士を同じ保存先へ接続せず、各版を一覧から選べるようにする。

IndexedDB版6で`driveBindings`（送信待ち番号・アカウントID・固定の保存先ID・状態）と`driveSettings`（ランダムなブラウザ識別子）を追加。メール・氏名・トークンは保存しない。既存の本文・PDFは書き換えず、旧タブの書き込みは版違いで拒否する。古いタブを閉じて再読み込みし、サイトデータは削除しない。

編集・名前変更と送信番号は同一トランザクションで更新する。本文やPDFを待ち行列へ複製しない。送信完了は取得した番号までだけを記録し、その後の追記を保存済みにしない。ローカルの削除では本文・元PDF・一覧・待ち行列を同時に削除する。古い通信結果で削除済みノートを復活させず、Driveの保存内容は自動削除しない。

同じブラウザの複数タブはWeb Locksで直列化する。未対応・HTTPのLANアクセスなどで使えない場合は自動保存を有効にしない。開発サーバーの起動・ポート変更や実ブラウザのデータ初期化は行わない。

## 応答を失ったとき

初回のフォルダ・PDF・JSONに使う3つのIDを、[files.generateIds](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/generateIds)で取得し、送信より先に端末へ保存する。再試行では同じIDを使う。成功後に応答を失い作成が409になっても、既存の実体を検証する。[Google公式の予約IDによる重複防止](https://developers.google.com/workspace/drive/api/guides/manage-uploads#use_a_pre-generated_id_to_upload_files)。

JSON更新の応答を失った場合も、次回は世代と内容ハッシュを取得し、保存済みなら再送しない。更新直前のversion確認だけを原子的な競合防止と扱わない。今回の保護は端末・ノートごとに書込先を分ける設計と、同一ブラウザ内の排他制御によるもの。第三者によるDriveファイルの直接書き換えまでを完全に排他する保証はしない。

## 制約と残作業

- 再取得可能キャッシュの500MB制限・自動整理は未実装。現在は送信済みでも元PDF・本文をブラウザに保持する。自動保存のための本文やPDFの追加複製はしないが、異なるノートの追加では容量が増える。
- Driveを唯一の本体とする読み込み経路、端末間の自動取得・統合、フォルダ階層同期は後続。既存の手動保存ノートを自動保存先へ勝手に転用しない。
- ページを閉じた後、端末のスリープ・ブラウザの停止中の送信は保証しない。未送信は次回の再接続後に再開する。終了時の確認は対応ブラウザの補助で、iOS等では出ない場合がある。
- GIS token modelの期限を自動で延長しない。[Google公式の認可方式](https://developers.google.com/identity/oauth2/web/guides/use-token-model)に従い、トークンはメモリだけに保持する。
- 1件のPDF256MiB・JSON16MiBの既存上限を維持。初回のPDFハッシュ計算はPDF1件分の一時メモリを使い、通常更新では再計算しない。変更のたびに元PDF・ZIP・全ライブラリを送らない。
- 操作に必要なメタデータ・JSONの確認通信は残る。実Googleでの秒数・端末別の速度は未計測。PC・iPad・スマホ・公開環境での確認はこれから行う。

## 確認手順

不要なテスト用PDFで自動保存を有効化し、Driveへ現れることを確認する。線・付箋・白紙・見出しの変更とUndo / Redo後、Driveから別ノートへコピーして内容を比較する。通常編集で元PDF・コンテナが増えないことを確認する。通信を切って編集し、未送信表示と端末への保存、再接続後の反映を確認する。一時停止・再有効化、別タブ、別端末でも同様に確認し、別端末の版が残ることを確認する。実データは削除せず、ローカル削除の確認は不要なノートだけで行う。

`driveOutbox.ts`が永続状態、`driveAutosave.ts`が送信順序・再試行、`driveAutosaveRemote.ts`が予約IDとリモート検証、`DriveAutosavePanel.tsx`が有効化・表示を担当する。既存`localNotes.ts`に原子的な送信番号更新・削除を接続する。
